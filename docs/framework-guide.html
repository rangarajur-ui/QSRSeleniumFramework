You just joined this project. Sit down. We start from zero.

This page is a classroom, not a wiki dump. If you have 3 years of experience or you are a fresher, you should be able to open this file, follow it top to bottom, and know what each folder is for, what each class does, how they talk to each other, and exactly where execution starts when you run a TestNG XML.

Remember this one sentence Tests do not click buttons. Tests ask a page class to click. The page class asks BasePage to find the element and wait. BasePage uses the browser that DriverFactory opened in BaseTest.setUp(). That is the whole framework.

2. Simple analogy — a restaurant kitchen

Think of the QSR app as a restaurant. Our framework is the kitchen staff.

XML suite = the order ticket

It says which dishes (tests) to cook today: sanity, regression, or the full menu.

BaseTest = opening and closing the kitchen

Before every dish: turn on the stove (browser). After every dish: turn it off.

Pages = stations

Landing, Catalog, Customer, Payment, Order. Each station knows only its own tools (locators + methods).

Tests = the recipes

“Add biryani, fill name, pay with card.” A recipe never says “find XPath.” It says “use the catalog station.”

5. If I run the XML — from where does it start?

This is the question everyone asks on day one. You do not start inside a page class. You start at the XML. The XML is only a list. TestNG reads the list, then the real Java begins.

Example command:

mvn clean test -DsuiteXmlFile=src/test/resources/suites/sanity.xml
1
Maven wakes up (pom.xml)

Surefire plugin sees suiteXmlFile and starts TestNG. Libraries (Selenium, TestNG, Extent) are already on the classpath.

↓
2
TestNG reads sanity.xml

It sees the listener listeners.TestListener, the group sanity, and the class list: CatalogApiHealthTest, LandingPageTest, CatalogPageTest, CustomerDetailsTest, PaymentSummaryTest.

Only methods tagged @Test(groups = {"sanity", ...}) will run. Regression methods in the same class are skipped.

↓
3
Suite starts → TestListener.onStart()

Extent report file is created: reports/ExtentReport.html. Tester name, environment, browser, OS, Java are written at the top of the report.

↓ now TestNG loops: for each @Test method
4
TestListener.onTestStart()

A new row in the report. Author = tester name. Category = group (sanity). Device = chrome. Description comes from the @Test(description = "...).

↓
5
BaseTest.setUp() — this is @BeforeMethod

This runs before every test method, automatically. You do not call it. TestNG calls it because the test class extends BaseTest.

  1. DriverFactory.getDriver() → opens Chrome at the mobile size from config.
  2. ConfigReader.getProperty("qrCodeUrl") → image URL of the table QR.
  3. QRCodeReader.readQRFromUrl(...) → decodes the QR into the real catalog link.
  4. driver.get(catalogUrl) → browser opens that link.
  5. landingPage = new LandingPage(driver) → first page object is ready.
↓
6
Your test method finally runs

Example: verifyCanAddItemToCart(). It calls openCatalog(), then catalogPage.addItemToCart(...), then Assert.assertEquals.

When the page method says click(addButton), that is BasePage.click: wait until clickable → find element → click (or JS click if something overlays it).

↓
7
BaseTest.tearDown() — this is @AfterMethod

DriverFactory.quitDriver() closes Chrome. Next test gets a fresh browser. That is why tests do not pollute each other.

↓
8
Listener writes the result

Pass → green line in Extent. Fail → red line + exception + screenshot from ScreenshotUtils. Skip → orange.

↓
9
Suite finished → TestListener.onFinish()

ExtentReportManager.flush() saves the HTML. Open reports/ExtentReport.html in a browser. That is your evidence.

Teacher says If you put a breakpoint, put the first one in BaseTest.setUp(), not in the XML. The XML has no Java. It only points. The first Java that always runs for a UI test is setUp().

6. One test, second by second (full order)

You run only e2e:

mvn clean test -DsuiteXmlFile=src/test/resources/suites/e2e.xml

e2e.xml includes group e2e and class tests.FullOrderFlowTest. That class has one method: verifyFullOrderFlowEndToEnd.

ClockWho is runningWhat happens on the screen / in code
0TestNG + ListenerReport row created. Tester + environment logged.
1BaseTest.setUpChrome opens. QR decoded. Catalog URL loaded. landingPage ready.
2openCatalog()If welcome screen exists → click Start Your Order. Else catalog is already there (table has an active session).
3CatalogPageRead price, click Add, assert quantity is 1.
4clickViewCart()Returns a CustomerDetailsPage. This is how pages are chained.
5CustomerDetailsPageProceed is disabled. Fill name + mobile from TestData. Proceed enables.
6clickProceed()Returns PaymentSummaryPage.
7PaymentSummaryPageOpen bill, read total, close bill, add AED 10 tip.
8Payment iframeChange payment → Debit/Credit → switch into iframe → type test card → Pay.
9OrderCompletionPageWait for order ID and brand name. Open bill. Pass.
10tearDown + listenerBrowser closes. Report flushed.
Why does a page method return another page? Because that is how a real user walks. View Cart takes you to customer details. So clickViewCart() returns new CustomerDetailsPage(driver). The test does not guess the next screen. The page tells you.

7. Page Object Model — in student words

Wrong way (do not do this in a test):

driver.findElement(By.xpath("//button[...]")).click();

Right way (what we do):

catalogPage.addItemToCart(TestData.MENU_ITEM);

If the XPath changes tomorrow, you fix it in CatalogPage once. Twenty tests stay untouched. That is the use of POM.

Rule of this project:

  • XPath / id / css live only in pages/.
  • Wait + click + type live only in BasePage.
  • Asserts and steps live in tests/.
  • URLs and names live in config.properties.

8. Root files — what is the use?

config.properties

The brain of data. Change the menu item name here, every test picks it up. Jenkins can override any key:

mvn test -Dbrowser=chrome -Dheadless=true -DtesterName="Rangaraju R" -Denvironment=QA

Useful keys: browser, headless, environment, testerName, qrCodeUrl, explicitWait, menuItem, cardNumber.

pom.xml

Maven shopping list + run instructions. Selenium, TestNG, Extent, Rest Assured, WebDriverManager live here. Surefire says: “run this XML.” Default is testng.xml. Jenkins passes another XML with -DsuiteXmlFile=....

testng.xml

Default full suite. First runs all sanity methods, then all regression methods (that includes the payment e2e). Sequential, not parallel — one table QR is shared.

Jenkinsfile

A Jenkins job reads this instead of you typing Maven. You pick suite, browser, tester name, environment. After the run it archives reports/ and publishes Extent as HTML.

9. Folder base — the parents

Two classes. If you understand these, you understand 70% of the framework.

Class BasePage — use: every page’s toolbox

Connected to: all classes in pages/ (they extend BasePage). Uses ConfigReader for wait time.

MethodWhat is the use?
click(locator)Wait until the element is clickable, then click. If a popup blocks it, click with JavaScript.
type(locator, text)Wait until visible, clear the field, type the text.
getText(locator)Wait until visible, return the text (price, order id, welcome message).
scrollIntoView(locator)Scroll the element to the center. Used before View Cart.
isDisplayed(locator)True if it becomes visible before timeout. False if not. No crash.
isPresent(locator)True if it exists in the DOM right now (no long wait). Used for “is welcome shown?”
You will not call these from a test They are protected. Only page classes call them. That is on purpose.

Class BaseTest — use: every UI test’s setup

Connected to: every test class except the pure API health check. Uses DriverFactory, ConfigReader, QRCodeReader, LandingPage, ReportLogger.

MethodWhen does it run?What is the use?
setUp()Automatically, before each @TestOpen browser, decode QR, open catalog URL, create LandingPage.
tearDown()Automatically, after each @TestQuit browser.
openCatalog()You call it in the testHandle welcome screen vs already-open catalog. Returns CatalogPage.
goToPaymentSummary()You call it in payment testsShortcut: add item + fill customer + proceed. So payment tests do not repeat 15 lines.
logStep(message)You call itWrites “Step 1 — …” into the Extent report.

10. config and constants

Class ConfigReader

Use: ConfigReader.getProperty("browser") returns chrome from the file, unless Jenkins passed -Dbrowser=firefox. System property always wins.

MethodUse
getProperty(key)String value. Throws if the key does not exist — so typos fail fast.
getProperty(key, default)Same, but returns a default if missing.
getInt(key)For waits and viewport size.
getBoolean(key)For headless=true/false.

Class TestData

Use: tests say TestData.MENU_ITEM instead of typing “Chicken Tikka Biryani (Boneless)” ten times. Values still come from config.

11. Folder driver

Class DriverFactory

Use: the only place that talks to ChromeDriver. ThreadLocal means if two tests ever run in parallel, each thread has its own browser.

MethodUse
getDriver()Create browser if missing, then return it. Called from setUp.
getDriverIfPresent()Return the browser only if it already exists. Listener uses this so a failed API test does not suddenly open Chrome for a screenshot.
quitDriver()Close browser and clean the thread. Called from tearDown.

It also applies deviceWidth × deviceHeight because this product is a phone-first table QR flow, not a desktop site.

13. Folder tests — every test case explained

A test class is not a page. It is a list of checks. Naming rule: verifyThingHappened.

LandingPageTest

TestGroupWhat is the use of this test?
verifyWelcomeMessageShowsTableInfo sanity Confirms the QR opened the right table welcome. If the table already has an active order, TestNG marks it SKIP (not fail) — that is expected.
verifyStartOrderOpensCatalog sanity The most basic happy path: can the guest reach the menu? Asserts restaurant name is not empty.

CatalogPageTest

TestGroupWhat is the use of this test?
verifyCanAddItemToCart sanity Core money path. If Add is broken, nobody can order. Asserts quantity becomes 1.
verifyQuantityIncreaseAndDecrease regression Plus → 2, minus → 1. Catches broken quantity controls after UI changes.
verifyCartSummaryBarAfterAdd regression Bottom bar must appear so the guest can go to checkout.
verifyMenuSearch regression Search “Biryani” and the known item must still be listed.

CustomerDetailsTest

TestGroupWhat is the use of this test?
verifyProceedDisabledUntilDetailsFilled sanity Empty form = Proceed off. Name + mobile = Proceed on. Protects against placing an order with no guest info.
verifyNameAloneDoesNotEnableProceed regression Name without mobile must stay blocked. A common validation bug.

PaymentSummaryTest

These stop before paying. Safer to run often. They use goToPaymentSummary() from BaseTest.

TestGroupWhat is the use of this test?
verifyPaymentSummaryShowsTotal sanity After details, a payable total must be visible. If this is blank, checkout is dead.
verifyBillDetailsCanBeOpened regression Guest can open and close the bill drawer.
verifyTenDirhamTipCanBeAdded regression Tip chip is clickable and total remains visible.
verifyChangePaymentToCard regression Change payment → Debit/Credit Cards. Does not enter the card. That is e2e’s job.

FullOrderFlowTest

TestGroupWhat is the use of this test?
verifyFullOrderFlowEndToEnd e2e regression The business proof. Catalog → customer → tip → sandbox card → order id. If only one test can run before a release, run this.

CatalogApiHealthTest no browser

TestGroupWhat is the use of this test?
verifyCatalogApiIsHealthy sanity Does not extend BaseTest. Hits the catalog API. 200 + restaurant name. If this fails, the UI tests will fail too — start here when the env is down.

CatalogApiTest

TestGroupWhat is the use of this test?
verifyItemPriceMatchesBetweenApiAndUi regression API says 33.00, UI must say AED 33.00. Catches “backend changed, frontend still old.”
verifyCustomizableFlagMatchesUi regression If API says customizable, the UI must show the customisable label.

14. Listener + Extent report

You never call the listener. TestNG calls it because the XML has:

<listener class-name="listeners.TestListener"/>

Class TestListener

MethodUse
onStartCreate the report once for the whole suite.
onTestStartNew test node. Write tester, environment, browser, class, groups.
onTestSuccessMark PASS.
onTestFailureMark FAIL, print exception, attach screenshot if a browser exists.
onTestSkippedMark SKIP (welcome screen already used, or a dependsOn failure).
onFinishSave the HTML file.

Class ExtentReportManager

Use: the engine behind the pretty report. System info: tester, environment, application, browser, headless, base URL, OS, Java, time.

MethodUse
startTest / getTest / endTestOne report node per TestNG method. ThreadLocal = safe if we add parallel later.
step / info / pass / fail / skipThe words you see in the report.
addScreenCaptureAttach PNG next to a step.
flushWrite the file to disk. Without this the HTML is empty.
Where do I see tester name and steps? Dashboard header = system info from ExtentReportManager.
Each test left side = method name + groups.
Inside a test = Step 1, Step 2 from logStep() / ReportLogger.

15. utils and api

ReportLogger

Use: tests should not talk to Extent APIs. They say ReportLogger.step("Add item"), pass(...), screenshot(driver, "name").

ScreenshotUtils

Use: saves PNG under reports/screenshots/. Listener uses it on failure. Tests use it for important steps.

QRCodeReader

Use: the product starts from a table QR image, not a typed URL. readQRFromUrl downloads the image and decodes the link. That is why setUp does not use baseUrl alone.

CatalogApiClient

Use: POST to catalogApiBaseUrl + catalogApiPath + qrScanCode. Helpers: item price, customizable flag, in stock, restaurant name, table number. Used so UI and API can be compared.

16. TestNG XML suites — which ticket do I hand the kitchen?

FileWhat it runsWhen you use it
suites/sanity.xmlOnly sanity methodsEvery pull request / morning check. Fastest.
suites/regression.xmlOnly regression (includes full payment)Before a release.
suites/e2e.xmlOnly the card-payment flowWhen you only care “can we pay?”
suites/full-suite.xml or testng.xmlSanity block, then regression blockDefault mvn test.
Why not parallel? All UI tests scan the same table QR. If two tests order at once, the welcome screen and cart fight each other. So suites are sequential. Do not turn on parallel="methods" until we have many QRs.

17. How to run — copy these

# everything (testng.xml) mvn clean test # sanity only mvn clean test -DsuiteXmlFile=src/test/resources/suites/sanity.xml # one class from IDE # Right-click LandingPageTest → Run # Still goes: Listener → BaseTest.setUp → your method → tearDown # Jenkins-style overrides mvn clean test -Dheadless=true -DtesterName="Your Name" -Denvironment=QA

After the run, open reports/ExtentReport.html. That is the file you attach in a bug or a release mail.

18. When a test fails — where do you look? (teacher order)

  1. Extent report — which step was last green? The next step is the suspect.
  2. Screenshot — what was actually on screen?
  3. Was it setUp? — QR decode fail, env down, Chrome not opening. You never reached the test body.
  4. Was it a locator? — fix the page class, not the test.
  5. Was it test data? — item renamed on the menu? Change config.properties.
  6. Was it the shared table? — welcome skipped, old cart. Re-run once before you log a product bug.
If you remember only one path, remember this XML → TestListener → BaseTest.setUp (browser + QR) → your @Test → page method → BasePage.find/click → tearDown → Extent flush.
